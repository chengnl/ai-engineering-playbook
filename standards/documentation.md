# 文档目录与知识治理

本规范描述团队维护责任，目录、链接工具不证明语义正确。项目适配后在自己的AGENTS和知识入口指向唯一现行说明；不复制来源业务工程的角色、服务器或固定根文档清单。

## 目录、命名与索引

- **DOC-01 MUST** 总知识入口由project.json的knowledge_entry指定，默认docs/README.md。根README及知识入口只承担使用、导航和必要当前状态，不堆发布流水、固定历史通过数或互相矛盾的“最新通知”。
- **DOC-02 SHOULD** 根部只放入口与跨模块总览/契约；其余按职责分类。modules放现行功能，ai放模型/提示词规则，operations放可复用操作指南，guides放角色手册，experiments放未合并/已结束试验；architecture放决策与治理，plans放历史设计，acceptance放验收，releases放Git集成，deployment放环境执行，incidents放故障事实。按实际需求裁剪，不强制所有技术栈建立八份根文档或每类业务正文。
- **DOC-03 MUST** 每个使用中的分类有README索引，新主题加入所属索引；分类/常用入口变化才修改总入口。文件移动同步所有相对文件/标题/附件及脚本帮助引用，历史Git提交URL保留旧路径。不能创建空附件凑检查。
- **DOC-04 SHOULD** 现行文件使用稳定小写短横线名，用户手册允许清楚的中文名；历史记录新建为YYYY-MM-DD-topic.md。不要用latest/final/new之类复制多份“当前版”；已有历史命名可保留并明确范围。

## 当前、历史和实验

- **DOC-05 MUST** 当前主题整合描述最终实现：适用范围、规则、权限、触发、状态、关键数据/调用流、失败与兼容。直接修改/合并原章节并清除被替代现行描述，不在末尾追加日期“补充”而保留矛盾正文；更新时间是元信息，不是新流水章节。
- **DOC-06 MUST** 设计、验收、发布保留当时事实。方案被替代时注明替代日期、原因和现行主题链接；不能把未执行的方案写成上线、把历史通过数写成本轮通过。
- **DOC-07 MUST** 实验注明分支/版本、样本、结论边界、未验证项及环境，不宣称已默认启用。实验成为正式实现时整合入唯一现行主题，原实验保留来源及替代关系。源码、合入集成分支、本地运行和生产发布分别判断。
- **DOC-08 MUST** 当前功能规格保持唯一来源。若用specs/changes/<id>/记录本轮R/A/T和证据，docs/plans只作设计记录或引用，不再维护一套冲突的活跃规格；实现后将有效知识整合进modules等主题。

## 迭代检查与阶段复查

- **DOC-09 MUST** 每轮完成与提交/合并前，按实际diff更新受影响知识、根README及索引，清理本轮范围的重复正文、矛盾、过时状态、旧API/路径和失效引用。检查应用/接口/表/权限/模型/操作口径与文档一致；无影响项可说明不适用，不要求改遍所有文件。
- **DOC-10 MUST** 发布、里程碑结束或方案替代时，对受影响总览、模块、操作、指南及历史替代链接做阶段性人工复查。记录触发、范围、实际版本/环境、发现与处理、遗留风险/责任及复查条件。可并入验收/发布记录，复杂时使用knowledge-audit模板；不为小变更强制多写文件。
- **DOC-11 MUST** 发现文档与行为冲突先核对事实，不据旧文档盲改业务。范围外旧问题登记原因、影响、风险和复查条件，不将一次规范更新宣传为全仓历史已审计或全环境已更新。
- **DOC-12 MUST** 凭据、真实客户正文、数据库备份、截图/PDF/评测原始产物不进入知识库；使用脱敏示例和安全证据元信息。区分规则、工具覆盖和实际运行，人工语义审查、方案质量与阶段复查不能声称已自动生效。

## 项目适配

新项目初始化可生成带“尚无内容”声明的分类索引，只是治理骨架；按业务需要建立主题正文并移除不适用分类/链接。已有docs一律保留，人工归类后再修改索引，不由bootstrap移动、重命名或覆盖。

需要架构、API、数据库、权限等根总览时由项目明确稳定路径；不需要持久化的工具无需编造数据库知识。治理包标准位于.engineering/standards，项目本地技术例外另维护，避免复制成另一套冲突标准。

## 完成前检查

目录/命名归属 → 唯一现行正文 → 历史/实验状态 → 本轮差异和知识一致 → 索引/文件/锚点/脚本引用 → 安全 → 实际验证与遗留。check.py当前只检查有限的Markdown文件目标，不覆盖标题锚点、完整目录规范、过时语义或评审质量；其他项明确人工完成或未执行。
